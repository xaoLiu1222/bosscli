# 单岗位打招呼并发送图片（outreach）

## 目标与验收边界

本流程面向求职者自己的合法账号：**纯 Python 关键词搜岗位 → 用户选定一个岗位及其 HR → 明确确认一次 → 对该 HR 打招呼并发送一张图片**。不是聊天群发、批量触达或自动投递工具；一条命令最多处理一个搜索结果，不自动选择第一个岗位，也不遍历结果发消息。

**2026-11-11 已完成一次用户明确选岗确认的纯 Python 端到端实测：打招呼、上传图片及消息业务回执均成功。** 这是单账号、单岗位样本，不是所有账号与未来版本均可用的保证。现有证据分层如下：

| 层次 | 已知状态 | 不能据此推出的结论 |
| --- | --- | --- |
| 岗位搜索 | 开发阶段已获用户许可，真实关键词搜索曾返回 15 个岗位 | 不保证任意账号、城市、关键词或登录态都能成功 |
| IM 连接与认证 | 在获许可的验证中，TLS、MQTT CONNECT/认证、订阅 `chat`、PING/PINGRESP 均已 observed | 单独连接成功不代表消息发送成功；后续另完成了一次获确认的图片发布 |
| 订阅响应 | observed SUBACK 仅含匹配的 packet-id，granted-QoS 数组为空；实现接受此响应，不虚构服务端授予的 QoS | 不等于服务端承诺 QoS 1，也不是图片业务 ACK |
| 编码与保护逻辑 | MQTT、图片消息 protobuf、ACK 匹配、联系人上下文校验和 journal 逻辑已有静态分析/离线实现 | 静态结构或离线测试通过，不等于真实服务端已接受普通图片 |
| 完整单岗位流程 | 用户明确选择一个岗位与招聘者后，`friend/add` 返回 code 0；图片上传 code 0；取得匹配本次 clientMid 的正整数 serverMid，journal 持久状态为 sent；全程纯 Python，无 ADB 代发、无重试 | 业务回执证明服务器接收，不证明招聘者已读；不能外推其他账号/版本或批量发送能力 |

文档与测试不包含真实凭据、私钥、授权图片 URL 或图片正文。线上单次操作由用户明确授权，在开发验证过程中执行；日常运行仍须逐次选定目标并确认，不能把本次授权当作后续联系他人的授权。

## 前置条件与配置

- Python 3.10+，项目及其依赖已安装；`bosscli` 命令可用。流程运行时不需要手机、ADB、App 注入或手机端中转，但需要网络及有效账号登录态。
- session **由用户自己提供**，仅使用自己的求职者账号，不能套用他人账号数据或测试样本。登录态会过期；本命令不会绕过登录、验证码、频控或风控。
- session 至少需要 `t2`、`secretKey`、正整数 `uid`、`client_info`、`v`、`uniqid`，并保持同一账号及设备档案的一致性。`curidentity` 必须为 `0`（求职者）。搜索若需要 `cardlist_defaults` 中的账号专属期望岗位字段，也必须来自该账号。
- 必须配置 `session.im` 并提供本地 TLS CA、客户端证书和私钥。开发环境已有受保护的本地 TLS 材料，可在用户的私有 session 中配置其路径，无需运行时 ADB；这不等于公共仓库附带可用凭据，也不是图片发送验收。已有本地材料应保存在受保护的 `secrets` 目录，限制文件访问权限，**不要提交 Git、粘贴到聊天、打印到日志或打包到发行物**。不在代码中内置 APK 私钥，也不在运行时通过 ADB 提取材料。
- 默认聊天地址为 `chat.zhipin.com:443`，使用 TLS 并校验证书。不要关闭 TLS 校验来“修复”错误。

下面是**结构示意，不是可直接使用的有效 session**；尖括号内容全部要替换为用户自己的合法本地配置。证书文件名只作为示例，使用实际受保护文件的路径。不要拿示例中的值进行联网测试。

```json
{
  "t2": "<YOUR_OWN_T2>",
  "secretKey": "<YOUR_OWN_ACCOUNT_SECRET_KEY>",
  "uid": "<YOUR_OWN_POSITIVE_NUMERIC_UID>",
  "curidentity": "0",
  "v": "<YOUR_SESSION_APP_VERSION>",
  "uniqid": "<YOUR_OWN_SESSION_UNIQID>",
  "client_info": {
    "<KEEP_YOUR_OWN_CLIENT_INFO_FIELDS>": "<YOUR_OWN_VALUES>"
  },
  "im": {
    "host": "chat.zhipin.com",
    "port": 443,
    "ca_file": "secrets/im/server-ca.pem",
    "cert_file": "secrets/im/client.pem",
    "key_file": "secrets/im/client-key.pem",
    "timeout": 15
  }
}
```

- 上述字段位于 session JSON 的顶层；`session.im` 指顶层的 `im` 对象，不要再套一层 `session`。
- `client_info` 必须保留用户真实会话所需的完整档案对象或已有字符串；示意对象不是新的设备档案模板。
- `im.host` 默认 `chat.zhipin.com`，`im.port` 默认 `443`；实现仅接受已核实的聊天域名及 TLS 443，不支持任意中转服务器。
- `im.ca_file`、`im.cert_file`、`im.key_file` 为必填本地路径；示例相对路径按命令的当前工作目录解析，跨目录运行时建议用绝对路径。
- `im.device_id` 可选；未配置时使用该 session 的 `uniqid`。不要为了排错任意伪造、轮换客户端身份。
- `im.timeout` 默认 15 秒，允许 1–60 秒；加大超时不能把不确定发送变成可安全重试。

**连接副作用：** 使用与手机相同 client 身份登录 IM，可能挤下手机或其他同 client 的已有 IM 连接。手机无需在线，但这不代表没有账号连接副作用；最终确认必须包含这项影响。不要并行运行同账号的多个 outreach 任务。

## 命令与一次确认

```text
bosscli --session SESSION outreach QUERY --image IMAGE --city NAME [--select N] [--expected-job-id JOB_ID] [--expected-user-id USER_ID] [--confirm] [--original] [--limit 10] [--journal JOURNAL]
```

**`--session` 是全局参数，必须放在 `outreach` 前面**，不是子命令参数。以下仅展示命令用法，不表示已执行，也不构成普通图片线上验收证明。

| 参数 | 含义 |
| --- | --- |
| `QUERY` | 搜索关键词，例如 `Python` |
| `--image IMAGE` | 要发送的一张本地图片；不是任意远程 URL |
| `--city NAME` | 目标城市名称，例如 `杭州` |
| `--select N` | 本次展示的搜索结果编号，从 1 开始；只选择一个结果 |
| `--expected-job-id JOB_ID` | 人工核对后批准的数字 `jobId`；必须匹配所选结果，不匹配立即停止。任何预置 `--confirm` 均必填，TTY 也不例外 |
| `--expected-user-id USER_ID` | 人工核对后批准的 HR 数字 `userId`；必须匹配所选结果，不匹配立即停止。任何预置 `--confirm` 均必填，TTY 也不例外 |
| `--confirm` | 对已明确选定的岗位、HR、图片和连接副作用给出预置写操作授权；必须同时提供上述双 ID pin，不是自动选岗开关 |
| `--original` | 保留原始图片字节，包含可能存在的 EXIF/GPS 元数据；默认不启用 |
| `--limit` | 最多展示的搜索结果数，默认 10；**不是发送数量** |
| `--journal` | 本地防重记录路径；省略时使用 session 所在目录的 `outreach.local.json`，后续运行应保持使用同一份记录 |

### 交互式终端（TTY）

```powershell
bosscli --session .\session.local.json outreach "Python" --image .\portfolio.png --city 杭州
```

推荐使用这种**不预置 `--confirm`** 的方式先查看当次候选结果；在当次 TTY 内选岗并输入 `yes`，无需预先填写双 ID pin：

1. 只读搜索并列出编号、岗位、公司、HR，以及数字 `jobId` 和 HR `userId`，核对这是否真是想联系的岗位和接收者。
2. 输入一个结果编号，不能输入多个编号；不会默认选中第一个结果。若提供 `--expected-job-id` 或 `--expected-user-id`，对应数字必须分别匹配选中结果，否则立即停止。
3. 核对最终摘要：岗位、公司、HR/接收者、数字 `jobId`/`userId`、图片名称/尺寸/字节数，以及可能挤下同 client IM 连接的副作用。列表及摘要中的外部文本会转义终端控制字符，避免其改写或伪造确认显示；仍须人工核对两个数字 ID，而非只看名称。
4. 只在确定后输入明确的 `yes`，一次确认涵盖**该岗位打招呼、该图片上传、该 HR 的一条图片消息和上述连接副作用**。空输入、否定、EOF 或取消均不视为授权。

**如果在命令行预置 `--confirm`，即使是 TTY，也必须同时显式提供 `--expected-job-id` 和 `--expected-user-id` 两个数字 pin，且分别匹配所选 `jobId`/`userId`；缺失或不匹配禁止写。** TTY 不预置 `--select` 时仍须当次输入编号；`--confirm` 不会代替选岗。

没有明确选择，或者没有最终确认，就不能打招呼、上传图片或发布图片消息。确认前允许只读搜索和本地图片准备；它不代表已有任何招聘者被联系。只指定 `--select N` 或两个 ID pin 也不能替代确认。

### 非交互式运行

当输入不是 TTY（脚本、管道、CI 等）时，默认只列结果、不写。必须**显式同时提供 `--select N`、`--expected-job-id JOB_ID`、`--expected-user-id USER_ID` 与 `--confirm` 四项**，才授权一次单岗位写操作；缺少任一个即禁止写。程序校验选中结果的数字 `jobId` 和 HR `userId` 是否分别等于两个批准的 pin，任一不匹配立即停止。只有编号与岗位 ID 仍不足以授权发送；招聘者变化也必须被阻止，不能只绑定岗位而忽略接收者。

下例 `2`、`123456789`、`987654321` 都是合成的示意占位数值，**不是实际获批的编号、岗位或用户 ID**。必须先以默认无写入模式列结果，人工确认目标及其显示的数字 `jobId`/`userId`，再替换这三个值；**不要原样执行发送示例，不得向这些合成 ID 实际发送**。

```powershell
bosscli --session .\session.local.json outreach "Python" --image .\portfolio.png --city 杭州 --select 2 --expected-job-id 123456789 --expected-user-id 987654321 --confirm --limit 10 --journal .\outreach.local.json
```

这里的 `2` 是**本次搜索结果的编号**，不是稳定岗位 ID；`123456789` 和 `987654321` 分别示意人工批准的数字 `jobId` 和 HR `userId`。搜索顺序、岗位状态和招聘者可能变化，双 ID pin 用于在选中其他岗位或接收者变化时阻止误发，并不是自动选择其他结果的条件。不要把命令做成定时任务、循环或面向多人复制的模板。需要最稳妥的当次选岗复核时，使用前述交互模式。`--confirm` 是实际打招呼及发送授权，不是 dry-run 标志。

## 被确认后实际发生什么

单次流程按顺序执行；失败立即停止，不跨过缺失信息继续猜测：

1. 将一个搜索结果绑定为岗位及接收者快照，校验岗位 ID、HR 用户 ID 等必要字段；不允许向当前账号自己发送。
2. 校验本地图片、账号配置和 TLS 材料；在打招呼/上传前建立并认证 IM 连接、订阅聊天。
3. 在本地 journal 先保存 `greeting_pending`，再对**选定岗位及 HR**调用 `friend/add` 打招呼。
4. 只接受成功响应 `zpData.relation`，校验其接收者及岗位归属，自动取得 **`relation.securityId`** 等聊天上下文。缺失、冲突或响应失败则停止；不会让用户手填聊天 token 来继续。
5. 使用该关系上下文调用既有图片上传模块（MD5 预检，必要时上传），取得原图/缩略图数据；随后编码并发布一条图片 IM 消息。
6. 仅收到匹配本次 `client_mid` 的业务回执并取得正整数 `server_mid`，才将 journal 标记为 `sent`。回执不是“HR 已读”的证明。

**两类 securityId 不能混用：** 搜索卡片的 `securityId` 只用于本次 `friend/add`；上传和聊天使用成功关系响应的 `relation.securityId`。用户不需要手工填写 `upload_defaults.securityId`，也不能把搜索 token、详情 token 或别人的关系 token 填进去替代。现有匹配联系人解析能力不意味着主流程可以跳过这一步的严格绑定。

上传成功本身**不等于发图成功**。TLS、CONNACK、SUBACK、PINGRESP、只有 packet-id 的标准 MQTT PUBACK，也都不能单独证明图片已成为业务消息。实现区分：

- 匹配 packet-id 和 `client_mid`、携带有效 `server_mid` 的扩展 PUBACK；或
- 匹配该 `client_mid` 的 protobuf type-5 `messageSync` 业务 ACK。

已完成一次该路径的真实验收：用户批准的单个岗位、招聘者和竖版图片严格绑定，取得匹配业务回执，journal 仅一条尝试且阶段为 `sent`，没有自动重发。此结论来自实际 serverMid 校验，而不是“代码写了等待 ACK”。返回 serverMid 不代表 HR 已读；其他目标、账号或版本仍可能被服务端拒绝。

### 图片与隐私

图片走既有本地准备流程：支持单帧 JPEG、PNG、WebP，默认按 EXIF 方向转换为 RGB JPEG、白底合成透明区，并不保留 EXIF/GPS 元数据。`--original` 则保留原始图片字节，**也保留其中可能存在的 EXIF/GPS 等敏感元数据**；只有核对原图内容和元数据后才应显式使用。输入及准备后图片受本地 20 MiB、4000 万像素安全上限约束；这些**不是测得的服务端限制**。outreach 不提供批量图片发送。

发送前请自行查看图片正文，移除不必要的身份证、手机号、住址、商业机密及他人信息。元数据清理不能清理画面中的隐私。不要打印或转发返回的授权图片 URL（authorized URL）；原始上传响应和异常调试输出也可能含敏感信息。

## journal、防重与不确定失败

防重键绑定 **同一账号 uid + 同一 HR/peer + 同一岗位 job + 准备后图片字节的 SHA-256**。不指定 `--journal` 时，默认记录位于 session 所在目录的 `outreach.local.json`。默认转码和 `--original` 可能产生不同字节，切换选项也可能改变防重键。这是本地去重约束，不是服务端全局幂等承诺：换记录路径、删文件、更换图片内容或更换账号，都可能绕开原有防重边界。

| 持久阶段/结果 | 含义与处置 |
| --- | --- |
| 无该尝试记录 | 尚无该防重键的持久发送尝试；仍需满足选岗与确认条件 |
| `greeting_pending` | 已准备请求打招呼，是否已到达服务器可能不确定；不能当作“没有打招呼” |
| `greeted` | 关系响应已通过本地绑定，后续可能失败；不要再次自动打招呼 |
| `uploaded` | 已取得上传结果，不能推断消息未送达或已送达 |
| `message_pending` | 图片发布即将或已经发出，但最终业务回执未持久确认；送达状态不确定 |
| `sent` 且有有效 `server_mid` | 同一防重键再次运行返回 `already_sent`，不再打招呼、上传或重发图片 |
| 任一未完成记录（partial/不确定） | 拒绝盲目重发，须先人工核实；不是可以自动续跑的队列 |

journal 记录账号/接收者/岗位标识、图片 SHA-256、消息 ID、阶段及错误类型，不存 `t2`、`secretKey`、关系 token、授权图片 URL 或图片原始字节。但它仍含个人关联信息，应保护权限且不提交版本控制。

- 发送前持久化阶段，发生超时、断连、进程退出或仅收到传输 ACK 后，**失败不等于未送达**。不自动重试打招呼、上传或发布，也不自动重连后补发。
- 对 partial/不确定状态，先在官方客户端人工核对指定岗位、HR、打招呼及图片记录，再决定后续处置。需要进一步发送时，必须另行明确确认；不能由程序自动作出“再发一次”的判断。
- **不要为“修复失败”轻易删除、清空或修改 journal，也不要改用一个新 journal 重跑。** 没有通用 `--force` 路径；保留原记录及脱敏诊断信息，先查明服务器实际状态。
- journal 损坏、格式不符或存在任务锁时应停止。锁可能来自仍运行的任务或异常退出；先核实进程和服务器状态，不要一看到锁就删除，也不要并发启动替代任务。
- 即使成功拿到回执，最终写 journal 的本地磁盘操作也可能失败；此时仍按不确定状态人工核实，不能凭终端“报错”就重发。

## 失败处置与使用范围

- 登录失效、证书缺失、TLS 校验失败、CONNECT/订阅被拒：停止，核实用户自己的 session 与本地凭据。不要打印 token、私钥、原始登录响应或授权 URL 来排错。
- `friend/add`、上传或业务 ACK 被服务器拒绝、触发验证码/风控/频控：停止本次流程，遵循平台规则处理，不换账号轮询、不绕过验证码、不修改客户端绕过服务端限制。
- 打招呼后发生任何错误：已有不可逆的外部副作用；按 journal 中的 partial/不确定状态处理，不把“发图失败”描述成“本次完全没写”。
- 搜索无结果、选择无效或缺少确认：不执行打招呼/图片上传/图片发布，不默认放宽条件联系其他人。

此功能只服务于有意且逐次确认的单岗位求职沟通：不支持聊天群发、批量 HR 触达、自动循环发图、规避平台配额或风控。获得本地命令授权不等于获得任意招聘者骚扰许可；服务器拒绝就停止。当前已有一次线上端到端验收，仍基于非公开协议，未来服务端或 App 更新可能影响兼容性。
